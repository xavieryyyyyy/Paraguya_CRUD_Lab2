# Practice, checks, and demonstration

Use disposable products and test accounts. Keep real passwords, SMTP values,
session cookies, and reset tokens out of notes/screenshots. Exercises below
ask you to predict behavior before checking the answer.

## A reading schedule you can repeat

Before session 1, read TERMS_AND_CONCEPTS.md sections 1-3: browser/server,
requests/methods, and routes/middleware. Pick one definition and point to its use
in web.php. Read its remaining categories as you encounter those terms in later sessions.

| Session | Read and open | Explain without looking |

Spend enough time on a session to write a short explanation and trace one concrete
value. Repeat the prediction exercises the next day, then a few days later and
a week later. Progress comes from recalling and applying the explanation, not
from assuming one long read will make every API permanent knowledge.

## Predict the behavior

### 1. Assignment and types

```php
$qty = 3;
$nextQty = $qty + 2;
```

What are the values afterward? Does qty change?

Answer: qty remains 3; nextQty is 5. The expression computes a new value assigned
to another variable. Assignment to nextQty does not automatically change qty.

### 2. An associative array

```php
$data = ['name' => 'Apple', 'qty' => 12];
```

What does data['qty'] return? What is the purpose of `=>`?

Answer: 12. The arrow associates the key qty with that value. This array is not
yet a saved Product; saving requires a model operation.

### 3. Browser required vs server required

Someone removes required from the Name input in browser Inspect. Does the server
accept an empty name?

Answer: no. ProductController's required validation still runs. Browser constraints
help the user, while server validation enforces input for direct/modified requests.

### 4. Fillable vs validation

Would adding qty to fillable reject -5 by itself?

Answer: no. Fillable permits that key for mass assignment. min:0 validates its
value. The database integer type alone is also not the complete input rule.

### 5. View name vs file path

Which file is selected by view('products.edit')?

Answer: resources/views/products/edit.blade.php. The controller must also pass
the Product object used by that view.

### 6. Product object vs collection

Why does index loop over products while edit reads product->name directly?

Answer: index receives a collection of records. edit receives one bound record.
The singular/plural variable names communicate that distinction; Laravel does
not infer it just from the English names.

### 7. When does create happen?

Does opening /product/create insert a row?

Answer: no. GET create returns a form. POST store validates and inserts.

### 8. Why a hidden PUT field?

The update form says method POST. How does it match a PUT route?

Answer: the hidden _method generated by @method('PUT') tells Laravel to treat
the request as PUT. Browsers do not natively submit this HTML form as PUT.

### 9. Guest can see a Delete URL

If someone knows a product's ID, does knowing its URL bypass auth middleware?

Answer: no. Middleware evaluates the request/session before the controller.
Knowing an ID does not grant login. A signed-in user still has access to the
shared records because we have no ownership policy.

### 10. Intended redirect

A guest opens /product/create, logs in, and there is no intervening change to
the saved intended destination. Which page should open?

Answer: Add Product, because intended redirects to the originally requested
protected page. The fallback Products page is used when there is no destination.

### 11. Checkbox value

Does Remember me save the user's plain password in localStorage?

Answer: no. LoginRequest passes its boolean to Laravel's guard, which uses its
remembered authentication mechanism. LocalStorage here stores only theme choice.

### 12. Password visibility

After Show changes input.type to text, does hashing stop?

Answer: no. It changes browser presentation. The form submits the same field,
and registration/reset controllers hash the password on the server.

### 13. Reset cooldown

Why does Please wait before retrying appear after a second quick reset request?

Answer: config/auth.php's password broker throttle is 60 seconds. This is not
the token expiration, which is 60 minutes. Keep the wait protection.

### 14. Password reset token

Is the hidden token input optional because the user cannot see it?

Answer: no. The broker needs it to verify the reset request. Invisible is not
the same as unused or confidential from the user.

### 15. Reset while already signed in

Why might an email link open Dashboard/another authenticated destination instead
of the reset form?

Answer: reset forms are guest routes; signed-in users may be redirected away.
Log out or use a private browser window to inspect the reset form as a guest.

### 16. Session clearing

Does logout remove products from MySQL?

Answer: no. It clears authentication/session information. Product deletion is
a separate controller/model operation.

### 17. Component mismatch

Why did using @extends('layouts.app') cause an undefined slot error?

Answer: that layout expects component content as slot. Inheritance provides
sections for yield. Product pages now extend layouts.product; auth uses x-guest-layout.

### 18. Flash vs timer

What does the five-second timer remove, and who created the success message?

Answer: JavaScript removes the rendered success banner. ProductController flashed
the message into the session during a redirect after the database operation.

### 19. Roles

Does auth middleware make a newly registered user an administrator?

Answer: no. It checks signed-in state. Our User data and routes do not establish
an administrator role.

### 20. Verification scaffold

The verify-email routes exist. Does that prove email verification is required?

Answer: no. User currently does not implement MustVerifyEmail, and the product
group requires only auth. Generated files can exist without full feature enforcement.

## Safe hands-on practice

1. Create a disposable product, note its ID, edit its quantity, and verify the ID
   remains the same. Explain which methods handle display and saving.
2. Submit invalid product input and locate the exact rule and view error block.
3. Log out and request a protected URL. Record the redirect before signing in.
4. Use an incorrect login password once, then the correct one. Explain the two
   checks: field validation and credential authentication.
5. Try registering with an existing email and mismatched confirmation. Explain
   why neither attempt should create a user.
6. Request a reset email, open the newest link while logged out, and reset a test
   account password. Point to the broker, hidden token, hash, and login redirect.
7. Switch themes and Show/Hide password. Explain why MySQL data does not change.
8. Shrink the browser for all four auth pages and list/add/edit product pages.
   Check labels/buttons/errors remain inside their panels and table scrolling
   happens inside its container.

Do not disable TLS, remove auth/CSRF, or reset the real database as a shortcut.
If practicing temporary validation changes, restore them immediately afterward.

## Demonstration order

1. Open `/` while logged out; show Login.
2. Show Register and its validation. For a required success screenshot, register
   a disposable new user; explain that registration currently opens Dashboard.
3. Show guest `/product` access redirecting to Login.
4. Sign in; show Products and one full CRUD round with a disposable product.
5. Show incorrect login rejection, logout, and the guest-access check again.
6. Show the delivered reset email with its URL/token obscured, then explain/reset
   through the current styled form.
7. Point to web.php's six auth-protected routes and auth.php's guest/account routes.
8. Answer the eight guide questions using the application examples.

Keep the PDF's eight deliverables in LAB3_ANSWERS.md beside the captured evidence.
Avoid filling screenshots with credentials or personal data that is not needed
to demonstrate the task.

## What was demonstrated, and what still needs manual checking?

The student demonstrated registration/login/logout, guest redirect, authenticated
CRUD, and successful reset email/password use through Mailtrap and Gmail. Login
rejection after the UI change was shown. Desktop screenshots show the customized
Login/Register/Forgot views in both themes; icons were added afterward.

Registration validation after the latest customization, final Reset Password
screenshots, long-term Remember me behavior, and narrow-screen checks for the
new auth/logout/password-viewer UI need explicit manual evidence. Automated
tests can cover server rules and redirects, but not replace those visual checks.
The final verification report is in VERIFICATION.md.

## Troubleshooting by layer

| Symptom | First place to inspect |
|---|---|
| Could not open input file artisan | Terminal folder; run inside app-crud |
| Route not defined | routes/web.php/auth.php and route:list |
| Undefined variable slot | Calling layout style: component vs section |
| View not found | Dot-name path under resources/views |
| Database refused connection | XAMPP MySQL and DB host/port 3307 |
| Nothing to migrate | migrate:status; already-run migrations are recorded |
| Password reset cooldown | Broker throttle; wait instead of repeatedly clicking |
| SMTP 535 | Provider username/full App Password, no masked placeholder |
| SMTP/connection/TLS error | Host/port/network/certificate settings; never share secrets |
| New password not accepted | Correct account, matching confirmation, newest valid link |
| Styles not changed | Correct public stylesheet; Ctrl+F5; stylesheet order |
| Vite manifest missing | npm install/build from app-crud |
| Inter not visible | Hosted font/network; inspect rendered font/fallback |
| Private value in screenshot | Remove it before publishing; rotate leaked credentials if needed |

## Independent mastery checks

After a day, explain Add Product without the guide. After a few days, explain
Login and a rejected guest request. After a week, explain reset email versus
reset submission, then draw the route/controller/model/view connections from
memory. Reopen the source and correct any missing steps.

For each method you read, answer: who calls it, what input it receives, which
checks can stop it, what data it reads/writes, and what response it returns.
For each visual script, answer: which DOM element it selects, which event/timer
runs it, which state changes, and whether any request reaches the server.
